Overview
Customs is a cost-aware swarm of cheap agents that hunts counterfeit listings, scam
promotions, and AI-video impersonation of a brand, then lets a human approve drafted
takedowns. The headline metric is dollars per verified infringement.
Working title: Customs (changeable). Event: Haunted Hacks, October 31, 2026, San
Francisco, with hacking from 11:00am to 4:00pm and submission at 4:00pm.
Pitch: a swarm that spends model dollars deliberately and remembers what worked, so
each hunt for a brand is cheaper and smarter than the last.
How it works: the user sets a brand, keywords, protected assets, and a budget. Scouts
(separate agents on cheap models) search different surf aces. Every candidate gets a f ast
triage decision from a pluggable decider (the OpenAI Decisions API, or a local Laya model
while access is pending), and the best candidates are verified with richer evidence. A
human approves or rejects drafted takedown notices. A per-brand actor stores the graph
of sites, listings, and sellers and learns which search lanes pay off . An orchestrator steers
the scouts live over Agent Relay , and all state lives in T erse Durable Actors.
Scope of this build: notices are drafted and approved but only simulated-submitted. The
demo is a live run on T esla and Musk with a recorded replay as the f allback.

Principles


PRD: Customs, a Cost-Aware Agent Swarm for Brand Abuse
1. Cost is a first-class constraint. Scouts reserve budget before spending, and a hunt
stops at its budget.
2. A human approves every takedown. Nothing is submitted automatically .
3. Results are candidates flagged for review , never accusations.
4. Memory compounds: each hunt should make the next one cheaper or f aster .
5. Scam content is opened only in a sandbox, never in the presenter's own browser .
6. Agent Relay carries coordination, and the actors hold state and make the rules.
7. Live and replay modes run the same pipeline.
Non-goals
Submitting real takedown notices.
Claiming deepf ake detection beyond classifying thumbnails and keyframes.
Scraping private groups or login-walled content.
Production-grade multi-tenant authentication.
Legal advice.
User flow
A hunt runs in eight steps, from setup to the labels that make the next hunt better .
1. Set up: the user enters the brand, keywords, protected assets (logos, official domains),
authorized sellers, a budget, and a precision-versus-recall setting. The server creates
the Hunt actor and loads the Brand and Playbook actors.
2. Assign: the orchestrator picks a lane for each scout from past hit rates per dollar and
sends each an assignment over Agent Relay .
3. Search and triage: each scout reserves a small amount of budget, searches its lane,
and triages every candidate with a Decisions API call.
4. Dedupe: each candidate goes to a Case actor whose id comes from the canonical URL,
so several scouts finding the same listing create one case.
5. Share leads: scouts message each other about sellers, domains, wallets, and channels,
and the server records each link as a graph edge.
6. Steer: the orchestrator watches yield per dollar and redirects scouts that are not
paying off .
7. Verify and draft: the best candidates get richer evidence and a second decision, then
a takedown notice is drafted for each verified case.

8. Approve and learn: the user approves or rejects each notice. Every decision is stored
as a label that updates the brand's whitelist, thresholds, and lane statistics.

Rules for building them
Methods run one at a time, so keep them short. Scouts and the server make model
calls, and actors only record the results.
Case ids come from the canonical URL, so duplicate reports collapse into the same
actor and report returns whether the caller was first.
Every snapshot carries a version number , and the UI ignores older versions, because a
Durable Actors release note warned that socket messages can arrive out of order .
Actor-to-actor calls are unverified, so the server calls each actor through its generated
client.
Canonical URLs: before hashing, lowercase the host, strip tracking parameters, and
normalize known short links, so the same listing always maps to the same Case.

Latency expectations
OpenAI says decisions take 100 to 180 ms, a vendor-reported figure.
A competitor's model card measured OpenAI's gpt-6-luna Decisions on images at 194
ms median and 334 ms p95 for 512 by 512, and 373 ms and 763 ms for 1024 by 1024. That
is indicative only , and I found no measurement for text with several questions.
A router reported GPT -6 Luna chat completions at 699 ms median and 7.6 s p95, so
scouts need timeouts.
Proposed target for triage: about 500 ms median and under 1.5 s at p95, including
network. Measure on real payloads first, run 8 to 16 calls in parallel, and keep
thumbnails small.
Pricing is $0.10 per million input tokens with no output charge, and image token pricing
is not published, so read each response's usage.
Reports differ on the question limit per request (400 versus 10), so ask at most 5. Send
images as base64 data URLs. Jev is text-only and cheaper at $0.042 per million tokens,
and OpenRouter also serves it.
Local Laya: reports of about 30 to 35 ms per decision and about 1.3 GB of RAM are
unverified on our hardware. Measure it on the event laptop, on CPU and on GPU, and set
its latency target from that run.

Interchangeable deciders
Every classification call goes through one Decider interf ace, so the OpenAI Decisions
API and a local Laya model are drop-in replacements chosen by configuration.
Why both. There is no Decisions API access yet, so Laya lets the team build and test the
whole pipeline offline. It also stays useful later as a free f allback when the hosted API
errors or rate-limits.
What Laya is. An open-weight decision model from ConvAI Innovations, released
September 18, 2026 under Apache 2.0. The English model has 421M parameters on
ModernBERT -large and a 512-token context, though one listing says 1k, so truncate to 512
to be safe. It returns typed answers with probabilities in one forward pass and generates
no text. Reports put it at about 30 to 35 ms per decision on a commodity GPU. It scores
well on binary safety-style calls such as spam (0.993) and phishing (0.980), and is weaker
on wide, fuzzy classification and ordinal scoring unless fine-tuned. It handles text only .

Rules that keep them drop-in
1. Same input, same output. Adapters normalize provider results into Answer, so the
shortlist, the actors, and the dashboard never depend on which provider answered.
Each case records the id of the decider that did.
2. Capabilities, not provider names. The cascade reads caps. For a text-only decider , an
image is replaced by a short text description (the listing text or OCR) or flagged as
visual evidence unavailable, which lowers confidence and raises review priority .
3. Canonical questions. Each adapter maps them to its provider's format. For Laya, a
predicate becomes a choice between yes and no, a mapping that is unverified.
4. Metering is adapter-agnostic. usage.usd comes from the adapter's price, which is
zero for local inference, and latency is recorded either way .
5. Limits live in the adapter . It truncates evidence to the model's context and splits
question sets to its question limit.
6. Calibration is per decider . Thresholds are stored in the Brand actor keyed by decider id
and never reused across deciders.
7. F allback chain. A timeout or error f alls through to the next configured decider , and the
answer carries the id of the decider that produced it.
